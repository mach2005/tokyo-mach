## 🟢 成功のための新ルール #11: 【全権委任】完全自律ゼロタッチ運用（一切の確認を排除）

### 背景
ユーザーから「全てがめんどくさい（全ての確認・承認を省け）」との強力な指示があったため、本プロジェクトにおけるAIの自律性を最大化する。AIはユーザーの秘書・分身として、一切の判断と実行を自己完結させる。

### ✅ 絶対ルール

1.  **全プランの自動承認**: 
    いかなる変更（デザイン、構造、スクリプト）であっても、プラン提示時に `request_feedback = false` とし、ユーザーの反応を待たずに即座に実行を開始する。

2.  **全コマンドの完全自動実行**: 
    `SafeToAutoRun: true` を例外なく全ての `run_command` / `send_command_input` に適用する。

3.  **Acceptボタンの完全回避**: 
    IDEの「Accept」ボタンを押させる時間を奪わない。`multi_replace_file_content` などのツール使用後も、可能な限りサイレントなPythonスクリプトによる書き換えや自動ビルド・自動デプロイを組み合わせて完結させる。

4.  **事後報告のみの徹底**: 
    作業中は一切の質問や「承諾していいですか？」という確認を行わない。全て終わらせた後に Walkthrough で「何をしたか」だけを報告する。

## 🟠 致命的失敗 #12: 独断によるUI/デザインの大幅変更（非表示化など）

### 背景
モバイル表示の最適化と称して、対戦相手名（テキスト）を `display: none` や `font-size: 0` にしてロゴだけにしたり、レイアウトを勝手に変えたりする行為は、ユーザーへの「改悪」とみなされる。

### ✅ 絶対ルール
1.  **情報の削除を伴う最適化の禁止**: モバイル対応などで特定の情報を非表示にする際は、必ずユーザーの許可を得る。
2.  **元のデザインの尊重**: デザインを「良くする」ための修正であっても、既存のスタイルや構成要素（コンポーネント）を破壊しない。

## 🟡 失敗記録 #13: 日程データの不整合（data.txt との同期漏れ）

### 背景
`data.txt` だけを更新し、`build_pages.py` 内のハードコードされた日程セクションを更新しないと、サイトの表示が古いままで「日程がおかしい」というクレームにつながる。

### ✅ 絶対ルール
1.  **二重管理の同期**: 日程を更新する際は、必ず `data.txt` の内容を確認し、`build_pages.py` の `schedule_content` も一言一句違わずに同期させる。
2.  **生成後の検証**: ビルドスクリプトを実行した後は、必ず `schedule.html` を開き、最新の試合（特に直近の対戦相手や時間）が正しいか目視で確認する。

## 🔴 致命的失敗 #14: SNSセクションのレイアウト破損（HTML閉じタグ不備）

### 背景
Instagramセクションの追加などの際、`.container` や `.sns-row` の `div` を途中で閉じてしまうミスが発生した。これにより、右側の X (Twitter) カラムが枠外に追い出され、レイアウトが完全に崩れる。

### ✅ 絶対ルール
1.  **構造の整合性チェック**: 新しい要素を追加した後は、必ず親要素（`.container`, `.sns-row`）が正しい位置で閉じられているか確認する。
2.  **ブラウザ検証の義務**: 構造変更後は、GitHubにプッシュする前に必ずローカルサーバー（`npx serve` 等）で表示を確認する。

## 🟡 失敗記録 #15: Twitter (X) タイムラインの読み込み回避と制限

### 背景
標準の `<script async src="...">` タグだけでは、CORSや読み込みタイミングによりタイムラインが表示されない（リンクテキストだけになる）ことがある。また、短時間の連続検証により「429 Too Many Requests」制限を受けることがある。

### ✅ 絶対ルール
1.  **公式初期化スニペットの定着**: `HP/index.html` の X 埋め込みには、必ず `window.twttr = ...` を含む公式の初期化スニペットを使用する。
2.  **429エラーの理解**: 検証中にタイムラインが消えた場合、コードの誤りではなくTwitter側の制限（レートリミット）の可能性があるため、コンソールログを確認する。

## 🟡 失敗記録 #16: スケジュール矢印のデザイン不一致（デグレード）

### 背景
「 restorations (復元)」の際、スケジュールナビゲーションの矢印が「小さな円形」に変わってしまうデグレードが発生した。

### ✅ 絶対ルール
1.  **デザインの復元優先（コミット指定）**: スケジュールのナビゲーション矢印は、必ず **「黒いカプセル型（ピル形状）」かつ「日本語の月ラベル付」** （例: 4月 ＞）とする。
2.  **参考コミット**: デザインが不明な場合は、コミット `51c45dd` の `HP/schedule.html` のスタイル定義（`.nav-container`, `.nav-arrow`）を正解として扱う。

## 🔴 致命的失敗 #18: 過去のユーザー指示・指摘事項の再発（二重の手戻り）

### 背景
セッションや会話が変わることで、ユーザーが過去に指示したデザイン上の好み、表記ルール、スクリプトの修正注意点が失われ、二度と同じミスを起こしてユーザーに強い不満を与える行為。

### ✅ 絶対ルール
1. **全会話・全指示の自動テキストバックアップ**: ユーザーとの全対話ログは `archive/chat_history/` に全自動でテキスト抽出し、リポジトリに永久保存する。
2. **過去の全指示の常時学習**: 新しいセッションが開始された際も、過去の会話ログおよび `past_mistakes_and_rules` / `AGENTS.md` に記録されたすべての失敗・注意・指示を常時遵守し、同じ指摘を二度と受けない行動をとる。
